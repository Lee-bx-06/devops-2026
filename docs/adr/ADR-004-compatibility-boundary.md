# ADR-004：兼容性策略——信封严格，载荷可扩展

- 状态：**已接受**（A1 谢浩天，A09；严格信封与可扩展载荷的边界经 B1 复核）
- 日期：2026-09-21
- 契约版本：1.0.0
- 相关：第 11、19、26 页；ADR-001、ADR-002

## Context

第 26 页把变更分成两类：

| 可兼容变化 | 可能破坏兼容 |
| --- | --- |
| 新增可选字段需要消费者允许 | 字段删除、改名或改语义 |
| 共享 Schema 同步更新 | 状态枚举改变 |
| 保留已有字段的含义 | 严格 Schema 拒绝新增字段 |

注意最后一行——**「严格 Schema 拒绝新增字段」本身被课件列为破坏兼容的风险**。
这与「共享 Schema 同步更新」存在张力：schema 太松，六个人各加各的字段，
公共契约名存实亡；schema 太严，任何一个服务想加一个自己需要的字段都会
被校验器拒掉，只能去改公共 schema，于是每次小扩展都变成全组同步升级。

A09 有六个人、四个服务、一份公共 schema。这个张力必须现在解决，
否则第 11 页要求的「需要自己决定：哪些字段是必填，名称是什么」
会在联调时以吵架的形式解决。

同时第 9 页只给了三个错误码，但四个服务实际需要的错误码远不止三个
（基线不匹配、幂等键冲突、产物写出失败……）。如果 `error.code` 是封闭枚举，
每加一个码都是「枚举改变」= 破坏性变更。

## Decision

**按「谁拥有这块 JSON」划分严格程度，一条边界线贯穿全契约。**

### 1. 顶层信封：`additionalProperties: false`（严格）

`create_request` / `job` / `artifact_record` 三个顶层对象，以及
`error`、`execution` 两个 A1 定义的公共子对象，一律拒绝未定义字段。

理由：这一层是六个人共享的**寻址与状态语义**。多一个顶层字段就意味着
所有消费方都要理解它，否则就是静默忽略——而静默忽略正是「字段改了语义但没人发现」
的温床。这一层要改，必须走 ADR + 升 `schema_version`。

### 2. `input` / `output` 载荷：**允许**追加字段（宽松）

服务专有载荷不设 `additionalProperties: false`。A2 可以在
`input.full_check` 里加自己的字段，B2 可以在 `output.draft` 里加，
不需要 A1 批准，也不需要升版本。

理由：这一层的消费关系是**点对点**的（BuildChecker → EChecker → MDFixer），
不是六方共享。第 26 页「新增可选字段需要消费者允许」——在这里，
「消费者」就是明确的那一个下游，他们自己协商即可。

约束：追加字段只能**新增可选**，不得删除或改名 A1 已定义的必填字段。
下游必须容忍读不到的字段（即不得依赖对方扩展出的字段作为硬前提）。

### 3. `finding`：九个字段必填，但允许追加

finding 是**跨组共享**的（A2/A3 产、B3 消费），所以第 10 页那套字段全必填；
但它同时是服务会想扩展的地方，所以不封 `additionalProperties`。

这是「严格」与「宽松」的组合：核心字段强制，扩展自由。

### 4. `error.code` 用命名空间正则，不用封闭枚举

```
^(VALIDATION_2[0-9]{3}|ENV_3[0-9]{3}|EXEC_4[0-9]{3}|ANALYSIS_5[0-9]{3})$
```

在已有命名空间内增码 = 可兼容变化，只需在 `errors.md` 注册表登记；
新增命名空间（如 `REPAIR_6xxx`）= 破坏性变更，需改正则 + 升版本 + 写 ADR。

这样既拦住了自由文本错误码（`BOOM` 会被拒），又不把六个人锁死在
三个码上。

### 5. `job_type` 与 `status` 保持封闭枚举

这两个**必须**严格。第 26 页把「状态枚举改变」明确列为破坏性变更；
第 25 页检查 02 又要求 `job_type=ABC` 被拒。它们是契约的骨架，
不能靠正则放行。

新增 `job_type`（比如 E3 要加第五个服务）= 破坏性变更，走 ADR + 升版本。

### 6. 版本号规则

`schema_version` 固定字符串 `1.0.0`，`const` 约束。

- **MAJOR**：破坏性变更（删字段、改名、改语义、改 `job_type` / `status` 枚举、
  新增错误码命名空间）。必须配 ADR，且四组样例全部同步更新。
- **MINOR**：可兼容变更（信封新增可选字段、新增错误码、`artifact.type` 新增取值）。
  需在本页与 `errors.md` 登记。
- **PATCH**：文档与样例修正，不改语义。

第 26 页「共享 Schema 同步更新」的执行方式：任何 MAJOR/MINOR 变更的 PR
必须同时改 `task.schema.json`、`tools/validate.py`（若涉及新约束）、
受影响的 `samples/`、`tests/`、以及相应 ADR。`make check` 不过不予合并。

## Alternatives

### 全部严格（处处 `additionalProperties: false`）

契约最干净，漂移无从发生。但第 26 页自己就把这条列为风险：
四个服务在 E3/E12 一定会需要新字段，每次都要 A1 改公共 schema + 升版本 +
六人同步，课堂 150 分钟内根本走不完这个流程，结果就是各组开始绕过校验器。**否决。**

### 全部宽松（不设 `additionalProperties`）

各组最自由。但公共信封会迅速长满只有一个人认识的字段，
`job_id` 可能被写成 `jobId`、`job_id_new` 并存，第 12 页「统一任务模型」
的验收条件「四类对象可表达」变成无法验证的口号。**否决。**

### 按服务拆分 schema，公共部分用 `$ref` 引外部文件

结构上最正统。但 E2 不部署、无 CI、无包管理，跨文件 `$ref` 需要解析器支持；
而 `tools/validate.py` 是零依赖手写的（ADR-006），引入外部引用会显著增加复杂度。**否决。**

### `error.code` 用封闭枚举，只允许第 9 页三个码

最严格、最不会用错。但四个服务真实需要的错误码远超三个，
每加一个都是破坏性变更，等于把 A1 变成所有错误码的审批瓶颈。**否决。**

### 不写版本规则，出问题再说

第 26 页整页都在讲这件事，第 11 页把「版本怎样变更」列为
「需要自己决定」的三项之一。不决定就是把决定权留给联调时的争执。**否决。**

## Consequences

**得到的：**

- 一条清晰的规则可以当场回答「我能不能加这个字段」：
  **加在信封里 → 要 ADR 和升版本；加在 `input`/`output` 里 → 自己加，告诉下游。**
- 各组能并行推进而不互相阻塞，这正是 A1 作为关键路径最该交付的东西。
- 破坏性变更有明确的触发清单，不会靠感觉判断。
- 错误码可以增长，同时自由文本码仍被拦住。

**付出的：**

- `input`/`output` 里的字段无人集中审查，可能出现两组各自加同名字段但语义不同。
  缓解：扩展字段建议加组前缀（如 `a09_*` / `b09_*`），已写入 `CONTRIBUTING.md`。
- 校验器无法发现「下游依赖了上游的扩展字段」这种隐式耦合，只能靠人工复核。
- 版本规则需要有人真的执行。E2 阶段由 A1 守门，`BACKLOG.md` 已记为待办。
- 严格/宽松的分界线需要向另外五个人解释清楚，否则会有人以为
  「信封严格」意味着整个契约都不能动。

**验证：**

- `samples/invalid/unknown-envelope-field.json` —— 信封加 `priority` → 被拒
- `samples/invalid/create-request-with-job-id.json` —— `create_request` 加 `job_id` → 被拒
- `samples/invalid/invalid-job-type.json` —— `job_type=ABC` → 被拒（第 25 页检查 02）
- `samples/invalid/pending-status.json` —— `status=PENDING` → 被拒（第 8 页枚举封闭）
- `samples/invalid/bad-error-code-namespace.json` —— `code=BOOM` → 被拒
- `samples/invalid/bad-schema-version.json` —— `schema_version=1.0` → 被拒
- `tests/…TestEnvelopeIsFrozen::test_service_may_extend_input_additively`
  —— **正向**断言：在 `input` 里加 `a09_extension` 仍然通过校验

最后一条尤其重要：它证明宽松的那一侧真的宽松，而不是一句空话。

**B1 已确认：** 信封严格、`input` / `output` 载荷可扩展；错误码注册表由 B1
维护。版本判定按 `../versioning.md` 执行；扩展字段的组前缀仍为建议约定。
