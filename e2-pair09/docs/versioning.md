# 版本与兼容性

| 项 | 值 |
|---|---|
| 负责人 | B1 |
| 版本 | v0.1 |
| 依据 | 《E2 需求与接口契约》第 11、26 页 |
| 适用对象 | `interfaces/task.schema.json`、`interfaces/endpoints.md`、`interfaces/states-errors.md` |

## 1. 版本号规则

契约版本写在每个请求与响应的 `schema_version` 字段里，形式为 `MAJOR.MINOR`。

| 变化类型 | 版本动作 |
|---|---|
| 新增可选字段、新增错误码、新增产物类型 | MINOR 加一，MAJOR 不变 |
| 删除字段、改名、改语义、改动状态枚举 | MAJOR 加一，MINOR 归零 |
| 修正文档错别字、补充样例 | 版本不变，只记 `CHANGELOG.md` |

当前版本 `0.1`。E2 结束前若契约内容仍在变，MAJOR 保持 0。

## 2. 可兼容变化

第 26 页列出的可兼容变化，转成我们这边的具体动作：

| 变化 | 需要谁同意 | 具体动作 |
|---|---|---|
| 新增可选字段 | 消费者允许即可 | 更新 schema、补一个用到该字段的样例、`CHANGELOG` 记一条、MINOR 加一 |
| 共享 Schema 同步更新 | A1 与 B1 双方 | 一方提改动，另一方复核后再合并 |
| 保留已有字段的含义 | 无人需额外同意 | 字段含义不得在 MINOR 内改变 |
| 新增错误码 | 消费该错误的组 | 按 `states-errors.md` 的命名规则扩展，MINOR 加一 |
| 新增产物类型 | 读取该产物的组 | 加入 `artifact.type` 枚举并补样例，MINOR 加一 |

## 3. 可能破坏兼容的变化

| 变化 | 为什么破坏 | 处理方式 |
|---|---|---|
| 字段删除 | 对方的解析或校验会失败 | 先新增替代字段，双方都切换后再删除。MAJOR 加一 |
| 字段改名 | 与删除等价，且错误更隐蔽 | 同删除流程，且必须两边同时改样例 |
| 字段改语义 | 字段名没变，对方不会察觉，属于最危险的一类 | 必须写 ADR，MAJOR 加一 |
| 状态枚举改变 | 对方的终态判断会失效 | 必须写 ADR，先与全部下游确认，MAJOR 加一 |
| 已有错误码改含义 | 对方的失败处理分支会走错 | 必须写 ADR，新增码代替改语义 |
| 严格 Schema 拒绝新增字段 | 对方按旧版本扩展字段时会被拒 | 本组已选定严格模式，见 ADR-002。扩展必须走第 4 节流程 |

## 4. 变更流程

1. 提出方在 `BACKLOG.md` 记一条，写明动机和受影响的消费者
2. 若属于破坏性变更，先写 ADR，状态为 Proposed
3. 与全部受影响的消费者确认，口头确认也要在 ADR 里记下确认人和日期
4. 改动落到 schema 与文档，同步补样例，反例也要补
5. 更新 `CHANGELOG.md`，递增 `schema_version`
6. A1 与 B1 双方评审后合并

破坏性变更在消费者确认前不得合并。

## 5. 消费者清单

改任何字段前，先在本表查它影响谁。

| 契约内容 | 主要消费者 | 确认人 |
|---|---|---|
| `input.repository`、`input.environment`、`input.build` | DRAFT、BuildChecker、EChecker、MDFixer | B2、A2、A3、B3 |
| `baseline` 相关字段 | EChecker | A3 |
| `md_report_uri`、`PATCH` 相关字段 | MDFixer | B3 |
| `finding` 结构 | MDFixer、以及所有读 MD 报告的一方 | B3、A2、A3 |
| `artifact` 结构与 `uri` 读取方式 | 全部四类服务 | 全组 |
| `status` 与 `error` | 全部四类服务 | 全组 |

这张表由 B1 维护。新增字段时如果找不到确认人，说明消费者还没确定，此时应先进 `BACKLOG.md` 而不是直接改 schema。

## 6. 与其他文档的关系

| 文档 | 承担的部分 |
|---|---|
| `adr/*.md` | 破坏性变更的理由与替代方案 |
