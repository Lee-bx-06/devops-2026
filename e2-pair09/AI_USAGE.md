# AI 使用记录

第 14 页要求写清"AI 提出什么、自己怎样判断、如何验证"。本文件按条目记录，做完一件事就追加一条，不要事后补写。

## 记录格式

| 项 | 说明 |
|---|---|
| 任务 | 当时要让 AI 做什么 |
| 提示摘要 | 给 AI 的关键输入，不需要逐字复制 |
| AI 建议 | 采纳前 AI 给出的内容 |
| 人工判断 | 采纳、修改或拒绝，以及理由 |
| 验证 | 用什么方式确认结果可用 |
| 关联 | 文件与提交 |

## 条目 1：按课件起草契约文档骨架

| 项 | 内容 |
|---|---|
| 任务 | 依据《E2 需求与接口契约》课件，起草统一任务模型、端点契约、状态机与错误码的初稿 |
| 提示摘要 | 提供课件中第 6 至第 10 页、第 19 至第 27 页的文本，说明 B1 角色范围与"E2 只定义不部署"的约束 |
| AI 建议 | 给出 `task.schema.json` 的结构、五个端点的清单、六个状态的迁移表、三个系统错误码的分组，并建议采用严格 Schema |
| 人工判断 | 部分采纳。课件明确写出的内容（状态取值、错误码、公共字段、端点命名）直接采用。课件没有规定的内容（错误码命名规则、`execution` 的字段构成、小报告是否内联、严格模式）标记为本组决定，逐条写进 `CHANGELOG.md`，其中严格模式单独写成 ADR-002 |
| 验证 | 用 `jsonschema` 校验 schema 自身合法性，并跑 3 个有效样例与 2 个反例，确认有效样例通过、反例被拒 |
| 关联 | `docs/interfaces/task.schema.json`、`docs/adr/ADR-002-strict-schema.md`、`docs/CHANGELOG.md` |

### 这条记录里需要人工复核的点

以下是 AI 补的部分，课件没有直接对应内容，必须由人确认后才能算定稿：

1. `execution` 的字段构成，特别是 `duration_ms` 与 `attempt` 是否够用
2. 错误码命名规则，是我们从三个示例反推出来的，课件没有明文规定
3. `incremental_check` 的 `baseline.commit` 必须等于 `base_commit` 这条约束，课件只说"检查基线提交和配置是否匹配"，没有给出具体判定
4. 重新验证环节中被拒绝的候选补丁，任务状态记为 `SUCCEEDED` 还是别的终态，课件只说明"失败时拒绝候选并记录原因"
