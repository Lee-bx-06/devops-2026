## 原始采集

脚本把当前仓库样例只读挂载到容器，再复制到本次独立证据目录。执行 `make clean` 后运行：

```bash
strace -ff -s 4096 -o trace/t -e trace=%file,%process make -p app > make-db.txt 2> build-stderr.log
./app > program-output.txt
```

`-ff` 将每个进程的系统调用写到独立文件；`%file,%process` 保留文件操作及进程创建/执行记录；`make -p app` 实际构建 app 并打印 Make 内部数据库。完整文本证据保存在 [evidence/241250033](evidence/241250033/)，二进制 `app`、`main.o` 保存在服务器原始目录及归档中。

## 从进程记录归到目标

本次进程关系为 `make(16) → cc(17) → cc1(18)、as(19)`，随后 `make(16) → cc(20) → collect2(21) → ld(22)`。

| 原始文件和行号 | 记录 | 解释 |
| --- | --- | --- |
| [trace/t.16](evidence/241250033/trace/t.16) 第 55 行 | clone 返回 17 | make 启动编译作业 |
| [trace/t.17](evidence/241250033/trace/t.17) 第 1 行 | `cc -c main.c -o main.o` | 当前作业目标为 main.o |
| trace/t.17 第 64、84 行 | clone 返回 18、19 | cc 启动编译器和汇编器 |

| trace/t.18 第 580 行 | 成功只读打开 config.h，返回 FD 4 | config.h 是该编译作业输入 |

`cc1` 读取源文件，`as` 写入目标文件；二者由同一个 cc 驱动作业启动，因此将这些读取归到 `main.o`。日志中的失败 `clone3(...)= -1 ENOSYS` 和搜索路径上失败的 `execve(...)= -1 ENOENT` 不产生新进程关系；后续成功的 clone/execve 给出了实际进程链。

## 人工 MD/RD 结论

| 目标 | 实际项目依赖 | Make 声明依赖 | 结论 |
| --- | --- | --- | --- |
| main.o | main.c、config.h | main.c、unused.h | MD：config.h；RD：unused.h |
| app | main.o | main.o | 两者相同 |

声明来自同次 [make-db.txt](evidence/241250033/make-db.txt)：第 1061 行是 `main.o: main.c unused.h`，第 609 行是 `app: main.o`。原始 [Makefile](evidence/241250033/Makefile) 第 6 行可作对照。

`config.h` 的成功打开记录明确出现在编译器 PID 18 中，但没有出现在 main.o 的声明依赖里，因此是 MD。修改该头文件后，当前规则可能不触发 main.o 重编译，留下旧产物。

`unused.h` 出现在声明依赖里；全部 7 份 trace 中，它只在 make 的 `trace/t.16` 第 46 行出现一次 `newfstatat`，用于查询文件元数据。没有成功读打开记录，编译和链接作业均未使用它，因此在本次编译配置下判为 RD。按当前 Make 规则，将该文件改得比 main.o 更新会触发不必要的重编译。

实际依赖按项目副本 `/evidence` 的路径范围整理；`/usr/include` 等系统头文件、工具链文件和 `/tmp` 中间文件不列入本次项目依赖集合。相对路径按进程工作目录解析；失败打开和单独的元数据查询不当作成功读输入。结构化人工结论见 [manual-analysis.json](evidence/241250033/manual-analysis.json)。

## 与论文方法的对应

论文：*Detecting Build Dependency Errors by Dynamic Analysis of Build Execution against Declaration*，Jun Lyu 等，所发 PDF 页眉标注 IEEE TSE 2025。

| 论文步骤 | 本次具体做法 |
| --- | --- |
| 第 4.2.1 节 Build Execution | 清理后跟踪真实构建，以 strace 记录进程和文件操作；根据 cc 的子进程关系关联输入与输出 |
| 第 4.2.2 节、算法 1 Build Declaration | 用 `make -p app` 取得展开后的 Make 数据库，定位目标的 prerequisites |
| 第 4.2.3 节 Modeling Build | 按 main.o、app 分别整理实际依赖和声明依赖 |
| 第 4.3 节、算法 2 Build Verification | 在项目范围内计算实际减声明得到 MD，声明减实际得到 RD |

论文使用基于 ptrace 的跟踪和自动分析，评估了 30 个项目；本次使用 strace 采集单个 GNU Make 小样例并人工解释，未运行论文的大项目性能对比。样例只有一个 Make 进程，每个构建作业产生一个最终目标；本次结果对应当前源码和编译配置。
